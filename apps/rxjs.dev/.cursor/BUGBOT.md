# rxjs.dev — Bugbot Rules

Applies when reviewing changes under `apps/rxjs.dev/`. Authoring reference: [.cursor/rules/rxjs-dev-site.mdc](../../../.cursor/rules/rxjs-dev-site.mdc).

## Generated vs hand-written

If the PR edits generated API documentation JSON or other dgeni output (paths that are regenerated by `yarn workspace rxjs.dev docs`), then add a blocking bug titled **"Do not edit generated API docs"** with body: "Edit JSDoc in `packages/rxjs/src/` and run `yarn workspace rxjs.dev docs`. Only edit markdown directly under `content/` for guides and deprecations."

If the PR adds narrative documentation for a new public operator only under `content/` without JSDoc changes in `packages/rxjs/src/`, then add a blocking bug titled **"API docs belong in JSDoc"** with body: "API reference is generated from JSDoc. Update source JSDoc first; use `content/guide/operators.md` for catalog listing, not as the sole API doc."

## Content changes

If the PR adds or changes a **public** operator listing in `content/guide/operators.md` but the operator is not exported from `packages/rxjs/src/index.ts`, then add a blocking bug titled **"Docs reference non-exported operator"** with body: "Guide listings must match actually exported public API."

If the PR introduces breaking or deprecation behavior in library code but does not update `content/deprecations/` when user-facing migration notes are required, then add a blocking bug titled **"Missing deprecation documentation"** with body: "Document breaking changes and deprecations in `apps/rxjs.dev/content/deprecations/`."

If Markdown or HTML content changes duplicate headings that are already rendered by the docs shell, add dead links, or add generic filenames for moved config/content files where the surrounding directory no longer gives context, then add a non-blocking bug titled **"Docs content drift"** with body: "Keep docs content aligned with the current app layout: avoid duplicated headings, stale links, and ambiguous moved filenames."

## App stack

If the PR adds tests using Mocha for site code that should use the app's Jasmine/Karma setup, or mixes test runners inconsistently with existing `apps/rxjs.dev` tests, then add a non-blocking bug titled **"Match rxjs.dev test runner"** with body: "Component tests use Jasmine/Karma (`yarn workspace rxjs.dev test`)."

If the PR adds non-null assertions in Angular app or docs-site tests to satisfy linting when the preceding code already asserts or guards the value, then add a non-blocking bug titled **"Avoid redundant non-null assertions"** with body: "Prefer the existing assertion/guard or a focused lint exception when needed. Do not add `!` that contradicts the test setup."
